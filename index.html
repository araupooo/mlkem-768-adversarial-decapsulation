Cross-implementation agreement (FIPS 203 ML-KEM-768 only)

  • Leg 1 (A ↔ C): same 64-byte seed 000102…3e3f loaded into pyca (from_seed_bytes) and Go (NewDecapsulationKey768); encapsulation by Go with pyca’s ek. Go encap ss, pyca decap ss, Go decap ss all identical (c55d3f85cf91d9b105c1fe0fd26cafc8ee31a074fbfd93454d5aac891db42947). Agree: yes.
  • Leg 2 (B ↔ A): keypair generated by liboqs; encapsulation by pyca with liboqs’s ek (from_public_bytes); decapsulation by liboqs. pyca encap ss == liboqs decap ss (bfa2c9673d165c1cf58aa15e19fb281212029c1002e6e441c9c1047ec41b02e9). Agree: yes.
  • All three FIPS 203 implementations agree (by transitivity of the two legs).

Findings

F-1 — Low: liboqs 0.12.0 and the Kyber reference do not enforce the FIPS 203 §7.3 decapsulation-key hash check

Corrupting one byte inside the stored H(ekPKE) region of the expanded decapsulation key (byte 2350 of 2400) and decapsulating a valid ciphertext yields a wrong 32-byte shared secret in 25/25 cases for liboqs and 25/25 for the Kyber reference — no error is raised. §7.3 requires the hash check H(dk[1152:2336]) == dk[2336:2368] before ML-KEM.Decaps runs. §7.3 permits the key check to be performed by means other than the decapsulating party, so this is a validation gap, not a standard violation. Callers must perform the §7.3 hash check themselves before handing a decapsulation key to liboqs. The Kyber reference predates FIPS 203, so the §7.3 framing applies to liboqs. pyca and Go store the key as the 64-byte seed, so the probe does not apply to them.

F-2 — Informational: fixed-size C APIs cannot enforce the §7.3 length checks; the caller must

liboqs (OQS_KEM_decaps) and the Kyber reference (crypto_kem_dec) take fixed-size buffers and assume a 1088-byte ciphertext and a 2400-byte decapsulation key. The harness wrapper enforces the §7.3 length checks before every call (400 cases NOT_INVOKED, zero C calls with a wrong-length buffer). pyca and Go enforce the checks inside the API (wrong-length ciphertext → error; wrong-length key rejected at load).

F-3 — Positive: implicit rejection is uniformly correct across all four implementations

950/950 adversarial-input cases returned a 32-byte rejection secret different from the valid secret, with no error and no crash — exactly FIPS 203 §6.3 Algorithm 18. Corrupting the z-region leaves valid-ciphertext decapsulation unchanged (25/25 MATCH per implementation), because z is only consumed on the rejection path (J(z‖c), step 7).

F-4 — Positive: the three FIPS 203 implementations agree on shared secrets

Cross-implementation agreement holds in both legs (see above). No distinguishable failure, non-rejection secret, or crash was found in any of the 2100 cases.
